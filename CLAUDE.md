# Контекст форка (levnas)

Форк `samosvalishe/free-turn-proxy` под ветку VK-TURN: обход операторских белых
списков через вайтлистную инфраструктуру VK Звонков. Трафик семьи, не эксперимент.

## Принцип работы с этим репозиторием

**Апстримный код не трогаем.** Только новая реализация интерфейса + точечные врезки
в диспатч — патч обязан переживать rebase на upstream.

`wire_hub.py` восстанавливает врезки после rebase, идемпотентен. **Три точки, не две:**

| Файл | Что |
|---|---|
| `internal/config/config.go` | `ProviderHub`, `HubOpts`, флаги `-hub-url`/`-hub-pin`, ветка валидации |
| `cmd/client/main.go` | `case config.ProviderHub` в `buildProvider` |
| `mobile/mobile.go` | **своя копия `buildProvider`** — без неё провайдер не доедет до сборок `gomobile bind` |

После прогона: `gofmt -l . && go build ./... && go test ./...`

## Проверенное по исходникам — не перепроверять заново

Всё ниже сверено с кодом v2.0.2. Каждый пункт когда-то стоил сессии.

- **Потолок полосы не в транспорте.** `kcptun.go:30-39` — `SndWnd=RcvWnd=512`, `MTU=1200`
  (не дефолты kcp-go). Это ~6.8 МиБ/с на стрим при RTT 86 мс; smux даёт ~11.6
  (`kcptun.go:124-131`). Наблюдается 0.137 МиБ/с на стрим — в полсотни раз ниже.
  KCP захардкожен (`config.go`, `KCPOpts`), флагов `-kcp-*` нет.
- **`rtpopus3` не режет пейлоад.** `rtpopus3.go:80` — `MaxWire = 56 + payloadLen`.
  Кадровая модель (шаг ts, VAD, пропуски seq) живёт только в полях заголовка.
- **TCP+bond и UDP/WG почти не делят кода** ниже wire-кодека: `bondframe`/KCP/smux
  есть только в TCP-тракте, `udprelay` идёт мимо. Обе ветки упираются в один
  диапазон → ограничение выше по течению, в тракте VK.
- **`bondframe.Reorder` (`bondframe.go:138-190`)** отдаёт байты строго по `Seq` —
  структурное head-of-line blocking между полосами. Не главный виновник (см. выше),
  но помнить.
- **`-streams-per-cred` только для `-provider vk`** (`config.go:190`, потребление —
  `main.go:204`). До hub-провайдера не доходит.
- **Мульти-линк:** `main.go` — `totalStreams = N * max(providerCount, 1)`, где
  `providerCount` для `-provider hub` берётся из `cfg.Hub.URLList()` (несколько
  `-hub-url` через запятую → `multi.Provider`, см. `internal/provider/multi`).
  Список из одного URL → `totalStreams = N`. Это объединение РАЗНЫХ аккаунтов,
  не relay-узлов одного креда — для этого см. `ServerAddrs` ниже.
- **`ServerAddrs` внутри одного креда уже ротируется, не только фейловерит**
  (`common.go:candidateIdx`, с 471c7fa от 2026-08-05): `DialTURN` стартует с
  кандидата `(streamID + j) % n`, так что разные стримы одного аккаунта сами
  разъезжаются по всем relay-адресам вместо того, чтобы все садиться на первый;
  на следующий кандидат по кругу переходит только при ошибке allocate. Это и
  распределяет нагрузку, и реально расширяет квоту (см. живой замер выше:
  10+10=20 вместо 10 на одном relay) — но дефолт `-n 10` эту ротацию не
  использует до конца, стримы 1-10 при round-robin по 2 адресам лягут
  примерно по 5 на каждый, до предела кластера далеко; поднимать `-n` к ~20,
  чтобы выбрать оба кластера полностью.
  ⚠️ `-turn` обрезает список кандидатов до одного (`common.go`, ветка `host !=
  ""`) — годится для экспериментов с конкретным узлом, но выключает и
  ротацию, и фейловер в бою.
- **`CredentialLifetime = 10m`** (`vkauth/types.go:37`) — под `-provider vk` клиент
  переминчивает креды каждые 9 минут на блок стримов. Hub-провайдер берёт реальный
  expiry из `username`, его это не касается.
- **`IsAuthError`** (`vkauth/cache.go:73`) — хук на ошибки TURN-allocate, а не на
  ответы VK API. Коды `4`/`102` до него не доходят.
- **Дисковый кеш кредов есть только у hub-провайдера** (`hub.go` `CacheFor`/
  `loadCache`/`saveCache`, с 471c7fa от 2026-08-05) — на случай недоступности
  хаба (блокировка IP оператором). У `-provider vk` кеша по-прежнему нет,
  только RAM (`vkauth/cache.go`).
- **`-obf-timing` запрещён в tcp-режиме** (`config.go:501-503`). Единственный рычаг
  регуляризации скорости недоступен на TCP+bond.
- **`scripts/install.sh:366-370` не знает `rtpopus3`** и делает `die`. `docs/flags.md`
  при этом актуален — расходится именно скрипт.

## Чего не делать

- Не коммитить секреты. `anonymToken`, Bearer hubcreds, `-obf-key`, UUID — только по
  ссылке на путь, никогда значением. Это форк публичного репозитория.
- Профиль обфускации на клиенте и сервере обязан совпадать. `none` = шейпер 64 кбит/с,
  любой замер без обфускации бессмысленен.
- **Квота аллокаций - по (кред, relay-кластер), не общая и не единая цифра
  [ПРОВЕРЕНО живьём 2026-08-08, свежий pool-аккаунт, оба relay-адреса из
  одного creds.json]:** 10 аллокаций на relay1 до 486, затем ещё 10 на relay2
  (relay1 НЕ освобождался) до его собственного 486 - итого 20 с одного
  credential'а. Значит: (а) квота по-кластерная (relay2 дал свежие аллокации,
  а не сразу 486, опровергает вывод от 2026-08-01 про общую квоту), но (б)
  предел на кластер оказался 10, а не 20 (опровергает недоказанную запись
  «40 = 20+20» от 2026-08-08 утром). Практический потолок ОДНОГО credential'а
  через штатные 2 relay-адреса ≈ 20 - это и есть то, что видно в консоли
  приложения, не баг и не недоделанный фикс. Чтобы пройти дальше 20, нужен
  второй **аккаунт** (`-hub-url` через запятую, см. «Мульти-линк» ниже), не
  более высокий `-n` на одном креде.
  ⚠️ Три замера подряд (2026-08-01, 2026-08-08 доксрока, 2026-08-08 живой)
  дали три разных числа - похоже, per-cluster предел плавает (аккаунт, время,
  нагрузка на relay). Держать как [ПРОВЕРЕНО] только на дату замера, не как
  архитектурную константу; при сомнении - мерить заново, не читать этот пункт
  как факт на будущее.
- Автообход капчи не делаем — анти-абузный механизм.
- Не удалять живой `creds.json` на хабе при работающих клиентах.

## Метод

Метки в отчётах: **[ПРОВЕРЕНО]** (живой прогон или исходник) / **[ГИПОТЕЗА]** /
**[ОТМЕНЕНО]**. Не гадать по README и поведению — смотреть исходник, лог, замер.

Позитивный контроль в замере обязателен: без него неотличимы «мёртвый токен» и
«кривой запрос», «медленный туннель» и «мёртвая цель» (на последнем потеряли сессию —
`speed.hetzner.de` просто снял A-запись).

Сначала считать, потом мерить: гипотеза про окна KCP снята арифметикой за пять минут.

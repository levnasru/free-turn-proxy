# Флаги

## Клиент

| Флаг | По умолчанию | Описание |
| --- | --- | --- |
| `-listen` | `127.0.0.1:9000` | локальный адрес `ip:port`, куда подключается WireGuard или Xray клиент |
| `-peer` | **обязательный** | адрес сервера на VPS, `host:port` |
| `-provider` | `vk` | источник TURN-creds: `vk` \| `hub` (см. `docs/providers.md`) |
| `-hub-url` | пусто | **обязательный для `-provider hub`**; URL эндпоинта с готовыми TURN-creds |
| `-hub-pin` | пусто | **обязательный для `-provider hub`**; base64 SHA-256 SPKI сертификата хаба |
| `-link` | пусто | (устарел) одна ссылка VK Calls `https://vk.ru/call/join/...`; используйте `-links`. Игнорируется, если задан `-links` |
| `-links` | **обязательный для `-provider vk`** (или `-link`) | ссылки VK Calls через запятую `https://vk.ru/call/join/A,https://vk.ru/call/join/B`; каждая даёт свой пул из `-n` стримов |
| `-n` | `10` | параллельных TURN-потоков; это потолок, не обязательный минимум - каждый поток ретраит независимо (с backoff при квоте), туннель работает и с частью потоков, недостающие сами доедут по мере снятия квоты/восстановления сети |
| `-transport` | `tcp` | транспорт до TURN-реле: `tcp` (TCP/TLS) \| `udp` |
| `-mode` | `udp` | режим туннеля: `udp` (UDP-релей для WireGuard) \| `tcp` (TCP-форвардер для Xray/sing-box) |
| `-bond` | `false` | распределять одно TCP-соединение по всем активным smux-сессиям (только с `-mode tcp`) |
| `-turn` | из creds | переопределить IP TURN-сервера |
| `-port` | из creds | переопределить порт TURN-сервера |
| `-obf-profile` | `none` | wire-профиль обфускации payload: `none` \| `rtpopus` (RTP/opus + ChaCha20-Poly1305 AEAD) \| `rtpopus2` (+ RTP header extension, ближе к WebRTC) \| `rtpopus3` (+ abs-send-time, VAD, имитация потерь, вариативный timestamp); должен совпадать с сервером |
| `-obf-key` | пусто | общий ключ для `-obf-profile != none`, 32 байта hex (64 символа) |
| `-obf-timing` | `0` | межпакетная задержка для RTP-мимикрии (напр. `20ms`); только с `-obf-profile != none` и `-mode udp`; `0` = выкл |
| `-gen-obf-key` | `false` | напечатать новый ключ и выйти |
| `-manual-captcha` | `false` | сразу ручной режим captcha (только `-provider vk`) |
| `-streams-per-cred` | `10` | потоков на один кеш VK-учёток (только `-provider vk`) |
| `-platform` | `desktop` | класс устройства персоны VK-auth (мобильность UA/device/client hints): `desktop` \| `mobile` (только `-provider vk`) |
| `-dns-mode` | `auto` | `plain` (UDP/53) \| `doh` \| `auto` |
| `-dns-servers` | пусто | свои UDP/53 резолверы, `ip[:port][,ip[:port]...]` |
| `-client-id` | авто | уникальный ID клиента (автогенерация если не задан) |
| `-sub` | пусто | URL подписки (sub.md) для получения списка серверов |
| `-debug` | `false` | debug-логи |

**`-n` в `-transport udp`:** с версии, включающей session affinity (см.
`docs/superpowers/specs/2026-08-23-udp-relay-session-affinity-design.md`),
`-n` в этом режиме означает не число параллельных TURN-потоков, а размер
"hot-set" - сколько сессий держать живыми одновременно, пока активной в
каждый момент времени является ровно одна (переключение по накопленному
объёму трафика, не по каждому пакету - так исправлен флаппинг WireGuard
endpoint'а при `-transport udp`). Практический эффект: то же число `-n`
теперь держит МЕНЬШЕ одновременных TURN-аллокаций, чем раньше. Семейные
профили (`-n 20/30/40`) подобраны под старую семантику "N независимых
потоков" - пересмотреть при следующем батч-релизе клиентов, не разово. В
`-transport tcp`/`tcpfwd`-режимах `-n` не меняет смысл.

**`-obf-timing`, откуда 7ms:** живой замер 2026-09-01 нашёл на TURN-сессии VK
жёсткий потолок ~150-210 пакетов/сек (не байтовый шейпер, размер пакета не
влияет; per-session, не общий на аккаунт/relay-узел). Пейсер уже применяется
независимо на КАЖДУЮ сессию (`internal/wire/shape`, вызывается из
`oneTURN` на каждый TURN-поток) - никакой дополнительной привязки per-peer
не требуется, только интервал. `7ms` ≈ 143 pps - под подтверждённым
100%-безопасным порогом (150pps), с запасом под ±10% jitter пейсера.
Проверено живым замером 2026-09-03 на K=40: стабильные ~3.5 МБ/с с 9-кратным
снижением дисперсии между прогонами. Задеплоено на прод.

## Desktop-клиент — режим `vk-turn (tun)`

Помимо `vk-turn` (SOCKS5-мост на `127.0.0.1:1085`) в меню `vkturn-desktop`
(см. `docs/desktop.md`) есть пункт **`vk-turn (tun)`** — весь трафик машины
идёт через TUN-инбаунд xray-core, а не только приложение, у которого явно
выставлен прокси.

- Требует права administrator/root: при выборе пункта `vkturn-desktop`
  сам запрашивает повышение (UAC на Windows, `pkexec` на Linux) и
  перезапускается тем же бинарником с внутренним флагом `-tun-elevated`;
  вручную запускать от администратора не нужно.
- В туннель уходит весь трафик машины, **кроме** LAN/приватных диапазонов
  (тот же список исключений, что в Android-клиенте).
- На Windows нужен `wintun.dll` (драйвер TUN, без него xray не сможет
  поднять интерфейс) — он вшит в `vkturn-desktop.exe` вместе с `client`/
  `xray` и распаковывается вместе с ними при первом запуске, отдельно
  скачивать не нужно. На Linux `wintun.dll` не нужен.
- macOS пока не поддерживается — только Windows и Linux.

## Сервер

| Флаг | По умолчанию | Описание |
| --- | --- | --- |
| `-listen` | `0.0.0.0:56000` | адрес прослушивания `ip:port` |
| `-connect` | **обязательный** | локальный backend `host:port` (WG `127.0.0.1:51820` / Xray `127.0.0.1:443`) |
| `-mode` | `udp` | режим туннеля: `udp` \| `tcp` (bond автоопределяется) |
| `-obf-profile` | `none` | wire-профиль обфускации payload: `none` \| `rtpopus` \| `rtpopus2` \| `rtpopus3`; должен совпадать с клиентом (описание профилей - в таблице клиента) |
| `-obf-timing` | `0` | межпакетная задержка для RTP-мимикрии (напр. `10ms`); только с `-obf-profile != none` и `-mode udp`; `0` = выкл |
| `-obf-key` | пусто | общий ключ для `-obf-profile != none`, 32 байта hex |
| `-gen-obf-key` | `false` | напечатать новый ключ и выйти |
| `-clients-file` | пусто | путь к JSON-файлу (`clients.json`) для включения авторизации по Client ID |
| `-debug` | `false` | debug-логи |

## Управление Client ID (Команды Сервера)

> [!NOTE]
> **Про авторизацию:** клиент **всегда** отправляет свой Client ID первой записью после DTLS-handshake, сервер **всегда** его читает - wire-контракт симметричен. Флаг `-clients-file` на сервере включает **проверку** ID по allowlist (`clients.json`). Без `-clients-file` ID читается и игнорируется.

Сервер содержит встроенные команды для управления файлом `clients.json` (горячая перезагрузка поддерживается автоматически, перезапускать сервер после изменений не нужно).

```bash
# Добавить или обновить клиента (max_streams=0 или пропущен = без ограничения)
./server clients add <client_id> ["Комментарий"] [max_streams]

# Удалить клиента
./server clients remove <client_id>

# Вывести список всех клиентов
./server clients list
```

`max_streams` - жёсткий потолок одновременных соединений с сервером **для этого
client_id**, который проверяется на сервере при каждом принятом DTLS-соединении.
Он не зависит от того, что клиент запросит флагом `-n`: если клиент пропишет
`-n` больше выданного лимита (случайно или намеренно отредактировав конфиг),
сервер всё равно примет только `max_streams` одновременных соединений, а
остальные попытки сразу сбросит.

По умолчанию команды работают с файлом `clients.json` в текущей директории. Если вы используете другой путь, задайте его через переменную окружения `CLIENTS_FILE`:
```bash
CLIENTS_FILE=/etc/free-turn-proxy/clients.json ./server clients list
```

### Управление через Docker

Если сервер запущен в Docker-контейнере (например, с именем `free-turn-proxy`), вы можете использовать команду `docker exec` для управления клиентами без необходимости заходить внутрь контейнера или редактировать файл вручную:

```bash
# Добавить клиента
docker exec -it free-turn-proxy /app/server clients add "my-client" "Комментарий"

# Удалить клиента
docker exec -it free-turn-proxy /app/server clients remove "my-client"

# Посмотреть список
docker exec -it free-turn-proxy /app/server clients list
```

> **Важно:** команды `docker exec` берут путь к файлу из переменной окружения `CLIENTS_FILE` контейнера. Это работает, только если контейнер запущен с включённой авторизацией (т.е. `CLIENTS_FILE` задан в `docker-compose.yml` и файл проброшен через `volumes`). Если авторизация выключена, `clients` пишет в эфемерный `clients.json` внутри контейнера, который сервер не читает. Путь должен совпадать с тем, что смонтирован и передан в `-clients-file`.

# UDP-relay session affinity — design

## Статус (обновлено 2026-08-29) — секции 3-5 ниже частично устарели

Реализация пошла не по этому плану: в ночь на 2026-08-24 single-active-slot
маршрутизация (секция 3) была откачена на голый round-robin по всем живым
слотам hot-set'а — прямая просьба пользователя после живого замера
показавшего, что маршрутизация 100% трафика через один слот разом упирает
суммарную скорость в потолок ОДНОГО relay-пути, убивая саму цель hot-set'а
(усреднение по пулу). Подробности отката и живой замер — `git log
--grep=dispatcher`, коммиты `9576206`/`9806826`.

Взамен пошёл параллельный трек — не "починить ротацию активного слота", а
автоскейлер РАЗМЕРА hot-set'а (K), K8s HPA-style, реализованный по шагам:

- **Шаг 1 (done, `9806826`)** — `slothealth.go`: пассивный per-slot сигнал
  (throughput + последний RTT через `Ping()`), только наблюдаемость, ни на
  `route()`, ни на размер K не влияет.
- **Шаг 2 (done, `c81811c`/`f70a524`)** — `gradient.go`: скользящий RTT-baseline
  + `suggestedHotSetSize()`, раз в `gradientLogInterval` печатает предложенный
  K в лог **как dry-run, не применяется**. Причина не применять сразу —
  см. `gradient.go`'s doc-comment: RTT растёт и под реальной деградацией
  пути, и просто когда канал честно забит (bufferbloat) — нужно накопить
  dry-run логи с живых сессий и сверить с фактической скоростью в момент
  просадки, прежде чем доверить этому сигналу реальное управление K.
- **Шаг 3 (done, `d37ddc7`)** — ручной live-ресайз hot-set'а на ±1
  (`growHotSet`/`shrinkHotSet` в `sessionmgr.go`), без автоматики.
- **Наблюдаемость (done, `4bfad41`)** — тики градиента пишутся построчно в
  CSV (`gradientLogFile`), не только в лог.
- **Шаг 4 (НЕ начат)** — автоматическое применение `suggestedHotSetSize()` к
  реальному K вместо dry-run — заблокировано на накоплении dry-run логов
  (см. Шаг 2). Не начинать без явного разбора логов.

Секции 3 ("Dispatcher и ротация по объёму") и 4 ("Обновление состава
hot-set") ниже описывают ПЕРВОНАЧАЛЬНЫЙ план, который в этой части не
реализован — оставлены как есть для истории решения, не как текущее
поведение. Секция 5 ("Failover") тоже устарела в части liveness-failover
активного слота — актуальное поведение см. в doc-comment `dispatcher.route()`.

## Проблема

`-transport udp` (Android WG-egress, `internal/proxy/udprelay`) поднимает N
независимых TURN+DTLS стримов к одному и тому же удалённому peer и
распределяет исходящие пакеты локального WireGuard-клиента между ними
**на каждый отдельный пакет**, случайно: все стримы читают из одного
общего `inboundChan` (`internal/proxy/udprelay/loop.go`), кто первый
вычитал — тот и отправил. На сервере (`internal/proxy/udpserver.Handle`)
каждый стрим — отдельный независимый UDP-сокет к WG-бэкенду, без какой-либо
склейки по сессии.

WireGuard хранит **один** активный `endpoint` на пира и переставляет его на
источник любого валидного входящего пакета (штатное поведение для роуминга).
При случайном чередовании стримов сервер дёргает свой "текущий endpoint"
между сокетами почти на каждый пакет.

### Собранные живые данные (2026-08-23, реальный профиль, SM_S938B)

- 60 стримов (2 hub-аккаунта × `-n 30`), лог показывает установку всех 60 за
  14с, ни одной ошибки/quota-сообщения. Реальная скорость через WG во время
  активной загрузки — ≈1 KB/s (после исправления заниженного в 3 раза
  показометра `SpeedMonitor.kt` — см. ниже, — истинное число ещё ниже).
- `-n 1` (минимально возможный набор): скорость упала в разы относительно
  привычного `-n 20`, стабильность сети тоже просела.
- 1 кред (1 аккаунт, свой N): 0.2 МБ/с. 2 креда (оба аккаунта): 0.4 МБ/с —
  чистое сложение по объёму.
- Но при этом с 2 хабами jitter 2мс→5мс, upload 166→127 (просадка, не
  рост) — при 1 хабе jitter/upload лучше.

### Интерпретация

Чистое сложение по объёму невозможно при буквальном параллельном
использовании (WG физически не может писать в два сокета одновременно на
одного пира) — значит наблюдаемый эффект это не бондинг, а **усреднение по
пулу во времени**: чем больше кандидатов, тем выше шанс, что "текущий" в
любой момент — быстрый узел. Полезный эффект. Но переключение на каждый
единичный пакет, без всякой привязки к качеству, даёт тот же механизм и для
джиттера/upside-down эффекта на upload — вредный эффект той же причины.

**Диагноз:** не "много стримов ломает WG" и не "мало стримов — плохо".
Проблема в частоте и слепоте переключения: per-packet, без учёта нагрузки
или качества.

## Цели

1. Убрать per-packet метание endpoint'а, сохранив пользу от разнообразия
   пула кандидатов (усреднение к быстрым узлам за время сессии).
2. Не тащить N живых TURN-аллокаций одновременно там, где реально
   используется одна за раз — снизить квоту/API-нагрузку на VK без потери
   стабильности при обрыве текущего пути.
3. Дать ручной способ форсировать переключение, когда деградация видна
   пользователю, но не ловится liveness-проверкой.
4. Никаких изменений на сервере — вся работа клиентская.

## Не цели

- Не пытаемся угадать точную топологию инфраструктуры VK — группировка по
  /24 это эвристика, не подтверждённый факт; если она не соответствует
  реальным кластерам, деградирует до случайного разброса без потерь (см.
  ниже "Группировка кандидатов").
- Не трогаем TCP+bond режим (`bondclient`/`bondserver`) — там уже есть
  `bondframe.Reorder`, проблема session-affinity для него не стоит так же
  остро (он и не пытается разносить один поток по N путям без склейки).
- Не меняем сервер (`internal/proxy/udpserver`) — он уже per-stream, ничего
  не знает и не должен знать про "активность".

## Архитектура

### Сейчас

```
WG (лок.) → listenConn → runListener → inboundChan (общий)
                                            │
                    (N стримов, каждый читает из inboundChan напрямую)
                    stream1.oneDTLS ─┐
                    stream2.oneDTLS ─┼─► TURN → сервер (N независимых сокетов)
                    ...              │
                    streamN.oneDTLS ─┘
```

### Предлагается

```
WG (лок.) → listenConn → runListener → inboundChan (общий)
                                            │
                                      dispatcher (новый, единственный)
                                            │
                              [активный слот hot-set]  ◄─ ротация по объёму
                                            │
                              hot-set (K живых, K << N):
                              slot1.oneDTLS ─┐
                              slot2.oneDTLS ─┼─► TURN → сервер
                              ...            │
                              slotK.oneDTLS ─┘
                                            ▲
                              (периодическое обновление состава
                               из объединённого пула кандидатов
                               обоих/всех hub-аккаунтов)
```

`dispatcher` — единственный читатель `inboundChan` (было: N читателей).
Он владеет указателем "текущий активный слот" и явно направляет туда каждый
дочитанный пакет. Никакой другой стрим `inboundChan` не трогает.

Важно: **активность — глобальная, не per-аккаунт.** Один dispatcher на весь
процесс, hot-set собирается из кандидатов ВСЕХ провайдеров сразу (не по
хаб-аккаунту отдельно) — иначе два параллельных dispatcher'а (по одному на
аккаунт) воспроизвели бы ту же проблему на уровне аккаунтов, что мы и
наблюдали в живом замере (просадка upload/jitter при добавлении второго
хаба).

## Компоненты

### 1. Session manager (новый, `internal/proxy/udprelay`)

Заменяет текущий цикл `for i := range numStreams { go maintainSession... }`
в `Run()`. Владеет:

- **Объединённым пулом кандидатов** — каждый кандидат несёт ссылку на своего
  провайдера (какой хаб-аккаунт его отдал), нужно для `GetCredentials`.
  Источник — `ServerAddrs` из первого успешного `GetCredentials` на каждого
  провайдера (уже есть в текущем коде, просто нужно сохранить у себя, а не
  выбрасывать после `candidateIdx`).
- **Hot-set'ом** — K активно поддерживаемых TURN+DTLS стримов (переиспользует
  существующие `oneDTLS`/`oneTURN`/`common.DialTURN` без изменений внутри
  них — меняется только то, кто их запускает и сколько).
- **Указателем на активный слот** — читает и переключает только dispatcher.

`-n` меняет смысл: раньше — "сколько стримов открыть параллельно", теперь —
"размер hot-set" (K). Это ломает совместимость с текущими профилями семьи
(`-n 20/30/40`) по смыслу числа, не по факту работы — нужно предупредить в
`docs/flags.md` и учесть при следующем батч-релизе клиентов (клиенты
обновляются пачкой, не по одному фиксу — см. существующую практику проекта).

### 2. Группировка кандидатов (по /24)

Чистая функция: `groupByPrefix24(candidates []taggedAddr) map[string][]taggedAddr`.
Ключ — первые три октета IP. Hot-set строится "не больше 1-2 на группу, до
достижения K" — сначала берём по одному из каждой ещё непредставленной
группы, при нехватке групп добираем вторыми из самых больших.

Если группировка не соответствует реальной топологии VK — вырождается в
почти случайный разброс по всему пулу, то есть не хуже, чем без неё (см.
"Не цели").

### 3. Dispatcher и ротация по объёму

Только dispatcher делает `<-inboundChan`. Считает байты/пакеты, отправленные
через текущий активный слот; после порога (нужно откалибровать эмпирически,
стартовая точка — конфигурируемая константа, не хардкод "навсегда") — молча
переключает активный указатель на следующий живой слот hot-set'а (round-robin
внутри hot-set, не через весь пул).

### 4. Обновление состава hot-set

Отдельный, более редкий цикл (не на каждую ротацию активного): периодически
закрывает одного члена hot-set'а (не активного — не рвём то, что сейчас
используется) и поднимает нового кандидата из ещё не представленной или
исчерпанной по времени группы. Цель — за время сессии прогнать через
hot-set больше кандидатов пула, не залипая на одном подмножестве весь сеанс.

### 5. Failover

- **Liveness** — переиспользуем существующий реконнект (аналог
  `maintainSession`): если активный слот умирает (DTLS/TURN ошибка,
  `PermDead`), dispatcher немедленно переключается на следующий живой слот
  hot-set'а, а session manager поднимает замену на месте умершего (как
  сейчас `maintainSession` делает для одного стрима).
- **Ручной триггер** — команда `rotate` через stdin запущенного процесса.
  И Android (`CoreProcessController`, `ProcessBuilder`), и `cmd/desktop`
  держат клиент как подпроцесс с уже читаемым stdout — симметрично
  добавляем чтение команд из stdin в `cmd/client/main.go` (новая горутина,
  `bufio.Scanner` на `os.Stdin`), без нового порта/listener'а. Для iOS
  (`mobile/mobile.go`, in-process через gomobile) — отдельная экспортируемая
  Go-функция `TriggerRotate()`, вызываемая напрямую, без IPC.

### 6. Сервер

Без изменений. `udpserver.Handle()` остаётся per-stream; неактивные слоты
просто не получают трафика и тихо простаивают до `udpIdleTimeout` (30 мин),
это уже штатное поведение.

## Побочная находка — не блокирует эту работу, чинится отдельно

`SpeedMonitor.kt` (`turn-proxy-android`) считает дельту `TrafficStats` за
3-секундный опрос, но форматирует и подписывает результат как "KB/s" без
деления на интервал — показометр в шторке врёт (занижает факт. скорость
в ~3 раза). Пользователь подтвердил желание починить — доменная правка в
другом репозитории, не входит в эту спеку.

## Тестирование

- `groupByPrefix24` — чистая функция, table-driven тест (пустой пул, один
  IP, несколько групп неравного размера).
- Логика ротации по объёму — счётчик и порог, тестируется без реальной сети
  (фейковые байтовые инкременты).
- Dispatcher routing — тестируется с фейковыми слотами (интерфейс, не
  реальный `oneDTLS`), проверяя, что пакет уходит именно в текущий активный
  слот и корректно перенаправляется после ротации/failover.
- Обновление состава hot-set — таймер-управляемый цикл, тестируем логику
  выбора замены отдельно от реального времени (внедряемый clock/ticker, как
  уже сделано в `internal/clientsdb` для `loadIfModified`).

## Открытые вопросы для этапа реализации (не блокируют спеку)

- Точный порог ротации по объёму (сколько байт/пакетов держать активный
  слот) — калибровать эмпирически на реальном профиле, не гадать заранее.
- Точный размер и период обновления hot-set — та же история.
- Название/семантика флага, заменяющего старый смысл `-n` (сам флаг `-n`
  переиспользуется под K, или заводится новый, `-n` при этом deprecated) —
  решить на этапе плана реализации.
